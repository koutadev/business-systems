# 意思決定ログ（Decision Log）

設計・方針の分岐点で「何を・なぜ選んだか／却下した案／背景」を記録する。行き当たりばったりでなく、根拠を持って判断した履歴を残す。
最終更新：2026-08-25

## 記録フォーマット
DEC-xxx｜日付｜対象｜決定｜背景・理由｜却下した案

---

**DEC-001**｜2026-08｜全体方針
- 決定：6種の業務システムを個別に作らず、共通基盤（テンプレ）を1つ作って派生させる。
- 理由：認証・権限・CRUD・DB設計・一覧基盤・CSV・ダッシュボードを共有でき、2本目以降を高速化。「共通基盤を設計して再利用する」こと自体が設計力の証拠になる。
- 却下案：各システムをゼロから個別実装（重複が多く非効率）。

**DEC-002**｜2026-08｜見せ方
- 決定：見た目はVercel静的デモ、中身はGitHub（Laravel実装＋設計README）で見せる2本立て。
- 理由：Laravelは静的ホスティングで動かず、ライブ運用はコスト増。静的デモ＋設計READMEなら費用ゼロで「デザイン」と「技術力」を両方示せる。営業軸（PHP/Laravel）ともズレない。
- 却下案：全システムをライブ運用（サーバー費用・保守負担）／フロントをNext.jsに寄せる（技術軸がJSに寄り営業軸とズレる）。

**DEC-003**｜2026-08｜CRM金額設計
- 決定：売上を内税（税込）で統一管理する。
- 理由：日本の販売・会計現場は税込基準が多く、帳簿との整合が取りやすい。
- 却下案：税抜管理（帳簿と二重変換が生じる）。

**DEC-004**｜2026-08｜CRM税率管理
- 決定：税率マスタを適用開始日で世代管理し、商品は標準税率を選択、商談明細は確定時点の税率をスナップショット保持。
- 理由：変動税率に対応しつつ、税率変更が過去の確定売上に影響しないよう保全する。日本の消費税改定は年度途中実施の歴史があるため「適用開始日」で持つ。
- 却下案：税率マスタを参照するだけ（変更で過去金額が変わる）／税率を年度で持つ（年度途中改定に非対応）。

**DEC-005**｜2026-08｜共通部品の展開方式
- 決定：共通基盤の部品をコピー＋同期スクリプトで各システムへ展開。
- 理由：composerパッケージ化やサブモジュールより運用がシンプルで確実。まず量産性を優先。
- 却下案：プライベートパッケージ参照（パッケージ化の手間）／Gitサブモジュール（運用が複雑）。

**DEC-006**｜2026-08｜CRM UX刷新のスコープ
- 決定：実サービス（Salesforce/GENIEE/Mazrica/ネクストSFA）を調査し、MUST＋SHOULDを実装（左ナビ・期間フィルタ両日付・保存ビュー・カンバン・コンボボックス・組織階層・予実）。
- 理由：「実サービス同等のユーザビリティ」を根拠を持って満たすため。調査で標準機能と確認できたものを採用。
- 却下案：自己流UIのまま（説得力に欠ける）／全機能フル実装（過剰、期間がかかりすぎる）。

**DEC-007**｜2026-08｜組織階層の粒度
- 決定：組織階層は「地域›エリア›店舗」の3段＋担当者。都道府県は階層に挟まず店舗属性＋任意の集計フィルタとして持つ。
- 理由：市場調査より、階層は「運用できる粒度・マネジメント単位」に収めるのが定石。都道府県は所在地属性でありマネジメント単位ではない。冗長化を避けつつ「都道府県で束ねて見る」ニーズも満たせる。
- 却下案：地域›エリア›都道府県›店舗の4段（冗長・入力維持コスト増）。

**DEC-008**｜2026-08｜予実管理の追加
- 決定：目標マスタ（全社/地域/エリア/店舗/担当者の粒度）を独立テーブルで追加し、達成率＝実績÷目標で可視化（ゲージ・目標ライン）。
- 理由：市場調査で予実管理はSFAの基本機能の一つと確認。実績は既存の受注集計を流用し、既存の金額・集計ロジックには影響させない。
- 却下案：既存テーブルに目標カラムを増設（既存レポートに影響・つじつま合わせになりやすい）。

**DEC-009**｜2026-08｜勤怠・受発注の扱い
- 決定：勤怠と受発注は別システムとして作るが、同じ架空クライアント（製造・卸）の世界観で揃える。統合版は全システム完成後の上位デモとする。
- 理由：案件は機能単位で発注されるため、別々に並べた方がポートフォリオの的が増える。同一クライアントで揃えることで実務感と統合版への布石を両立。
- 却下案：最初から統合システムとして作る（難易度が高く、実績づくり期には荷が重い）。

**DEC-010**｜2026-08｜進行管理の方針
- 決定：応募を逐次進めつつ、並行して残システムを開発。実案件を最優先、デモは需要ドリブンで作成。
- 理由：9月の給付終了に向け収入化を止めないため。実案件は匿名化すればデモより強い実績になる。
- 却下案：全システムを作り切ってから応募（収入化が遅れる）。

**DEC-011**｜2026-08｜予約システムの題材
- 決定：予約システムの題材を「オンラインヨガのレッスン予約」に決定。キャンセル待ち（繰り上げ）対応、モバイルファーストで設計。
- 理由：美容室予約は大手（ホットペッパー等）と競合。オンラインレッスンは予約枠・定員・競合防止・カレンダーという予約システムの核が主役になり、大手と競合しない。予約はスマホ利用が主のためモバイルファースト。
- 却下案：美容室予約（大手と競合）／月額オンラインサロン（予約でなくサブスク+コンテンツが主役で題材とずれる）。

**DEC-012**｜2026-08｜予約システムのMVPスコープ
- 決定：決済/月謝/チケット・振替・LINE連携・Zoom実連携・難易度分類/指名はMVP対象外（拡張点）。リマインドは仕組みまで作り実送信は拡張点。キャンセル待ちは繰り上げまで実装。
- 理由：予約の整合性（定員/二重予約/キャンセル待ち）とモバイルUXに集中。追加観点はMVP完成後に課題表で対応する運用試験とする。
- 却下案：最初から決済・全機能を実装（重く、MVPの趣旨に反する）。
